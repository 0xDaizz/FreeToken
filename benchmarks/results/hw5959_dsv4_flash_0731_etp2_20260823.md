# DeepSeek-V4-Flash-0731 ETP2 on hw5959

This is a hardware-specific validation of the ETP2 implementation introduced at
`25059e811a544781cfe329ec4189945df2931c63`, based on upstream
`0ab982f10905fa775962a4eddcb44caa50065251`. It is not an upstream project
claim or a pull-request result. The working fork is
[`0xDaizz/FreeToken`](https://github.com/0xDaizz/FreeToken), branch
`codex/dsv4-etp2-hw5959`.

## System and runtime

- CPU: AMD Threadripper 9970X, 32 physical cores.
- RAM: 256 GB quad-channel RDIMM (`251.048 GiB` visible to Linux).
- GPU: 2 x RTX 5090 32 GiB, each negotiated at PCIe Gen5 x16; no direct GPU
  P2P (`nvidia-smi topo -p2p r/w` reports `CNS`).
- Checkpoint: official `deepseek-ai/DeepSeek-V4-Flash-0731` revision
  `7872f01ba733b2cc04954c2c275d64e073de0040`, target shards 1--45.
- Runtime: `--tp-size 2 --disable-pynccl --expert-load serial`, ETP2 hybrid,
  2,048 logical cache slots, one maximum GPU fetch per rank, 12 CPU expert
  threads per rank, and `NCCL_P2P_DISABLE=1`.
- The 128--32K sweep used a 32,768-token pool. A separately validated
  65,536-token pool was used for the 48K/64K extension and accuracy suite.

## Streaming performance sweep

`benchmarks/bench_dsv4_stream.py` generated exact-token, unique prompts. Each
cell is the median of three uncached requests with 511 returned tokens,
temperature 0, greedy top-k 1, `ignore_eos=true`, and concurrency 1.

| Prompt tokens | TTFT (s) | End-to-end prefill approximation (tok/s) | Decode (tok/s) |
|---:|---:|---:|---:|
| 128 | 1.411 | 90.7 | 41.65 |
| 512 | 1.428 | 358.6 | 42.73 |
| 2,048 | 1.542 | 1,328.0 | 43.41 |
| 8,192 | 5.525 | 1,482.6 | 43.01 |
| 16,384 | 9.454 | 1,732.9 | 43.16 |
| 24,576 | 13.432 | 1,829.6 | 42.67 |
| 32,000 | 16.130 | 1,983.9 | 42.01 |
| 48,000 | 15.119 | 3,174.7 | 43.03 |
| 64,000 | 20.617 | 3,104.3 | 42.54 |

Definitions:

- TTFT is client POST start through the first non-empty streamed token.
- The prefill approximation is `(prompt_tokens - cached_tokens) / TTFT`; it
  includes scheduling and first-token decode and is not a kernel-only number.
- Decode is `(completion_tokens - 1) / (last_token_time - first_token_time)`.
- Every response reported `cached_tokens=0` and `finish_reason=length`.

Across the 18 requests at 512--32,000 prompt tokens, median decode was
`42.918 tok/s`. A linear fit to 8K--32K median TTFT gives a `2.002 s` fixed
intercept and `2,221 tok/s` marginal prefill rate (`R^2=0.9962`). The increasing
tokens/TTFT figure at longer prompts is mostly fixed-cost amortization and a
change in the full-layer prefill path, not a claim that attention gets faster
with context. At 64K, client-observed TTFT remained `20.617 s` and decode
remained `42.54 tok/s`.

The initial 128--32K sweep produced the following active-sample telemetry:

|---:|---:|---:|---:|---:|
| 0 | 92.52% / 95% | 273.36 / 358 W | 26,987 MiB | 23,358 MiB/s |
| 1 | 94.07% / 95% | 282.11 / 361.8 W | 26,585 MiB | 24,482 MiB/s |

The 48K/64K extension raised utilization and VRAM as expected but showed no
thermal or memory failure:

| GPU | Mean / median SM | Mean / p95 power | Max VRAM | Max temperature | Mean PCIe RX |
|---:|---:|---:|---:|---:|---:|
| 0 | 94.79% / 96% | 389.41 / 498 W | 30,135 MiB | 57 C | 26,561 MiB/s |
| 1 | 93.55% / 96% | 396.90 / 500 W | 29,733 MiB | 60 C | 26,800 MiB/s |

Earlier primitive measurements on the same checkout measured
`53.647/53.549 GB/s` per-GPU routed-expert gather and `107.278 GB/s` aggregate
simultaneous gather. An 8 KiB NCCL host-fallback all-reduce measured 15.50 us
median / 19.47 us p95. Compared with the FreeToken paper's `22--25 tok/s`
single-RTX-5090 DSV4 result, the measured `42.918 tok/s` dual-GPU median is
about `1.72--1.95x` as fast. The comparison is indicative because host CPU,
cache capacity, and exact prompt protocol differ.

## Liqbot coexistence

During the full accuracy run, a live coexistence snapshot showed:

| Cgroup / host metric | Bytes | GiB |
|---|---:|---:|
| FreeToken current | 153,994,731,520 | 143.42 |
| FreeToken benchmark runner current | 1,204,924,416 | 1.12 |
| `liqbot-shadow` current | 14,576,254,976 | 13.57 |
| Host `MemAvailable` | 31,187,120,128 | 29.05 |

Swap remained completely unused and memory PSI some/full was zero. Normal
Liqbot and FreeToken therefore coexist in 256 GB. The separate Liqbot
heavy-maintenance guard requires an 80 GiB host floor plus a 16 GiB admission
margin and the job's `MemoryHigh`; its rejection under this load is an
intentionally conservative admission policy, not evidence that the ordinary
services do not fit.

## Model-default-low accuracy suite

The local suite used Inspect AI 0.3.254 and inspect-evals 0.16.0 with
`temperature=1`, `top_p=1`, seed 424242, concurrency 1, a 50,000-output-token
cap, and omitted `reasoning_effort` (the server's model-default low profile).
AIME 2026, GPQA Diamond, and IFEval are their complete public task sets. The
MMLU-Pro row is a fixed 100-question control, not the full 12,032-question
source dataset.

| Task | Scope | Local result | Errors |
|---|---:|---:|---:|
| AIME 2026 | full 30 | 22/30 = **73.33%** | 0 |
| GPQA Diamond | full 198 | 146/198 = **73.74%** | 0 |
| IFEval prompt strict | full 541 | **85.40%** | 0 |
| IFEval prompt loose | full 541 | **89.46%** | 0 |
| IFEval instruction strict | full 541 | **90.41%** | 0 |
| IFEval instruction loose | full 541 | **93.16%** | 0 |
| IFEval final aggregate | full 541 | **89.61%** | 0 |
| MMLU-Pro | fixed control 100 | 84/100 = **84.00%** | 0 |

All 869 requested samples completed with zero request errors. The run took
about 4 h 20 min and emitted 525,892 output tokens. Aggregate output tokens per
sample wall time were `33.86 tok/s`; this is lower than the fixed-window decode
microbenchmark because it includes prefill, request boundaries, scoring, and
varied long reasoning outputs.

These low-profile scores should not be read as the model's maximum capability.
The local GPQA result is close to the preview checkpoint's official non-think
result (71.2) and far below its official high/max results (87.4/88.1). Current
proprietary frontier GPQA reports are roughly 92--95, subject to different
harnesses and inference budgets. The official 0731 model card instead evaluates
its code-agent profile at `reasoning_effort=max`, `temperature=1`, `top_p=.95`;
it reports 82.7 on Terminal Bench 2.1 versus Opus 4.8's 85.0, while larger gaps
remain on NL2Repo (54.2 vs 69.7) and DSBench-Hard (59.6 vs 71.7). A fair summary
is therefore **frontier-adjacent in low-profile general reasoning and broadly
competitive on agentic coding, but not at the current closed-model frontier on
all workloads**.

### Max-profile cap diagnostic

A separate one-question GPQA smoke verified that Inspect sent
`reasoning_effort=max` in the actual Chat Completions request. The model consumed
49,999 output tokens in 1,401.3 s, produced no final answer, and stopped with
`finish_reason=length`, yielding 0 for that sample. This is recorded as a
**50K-cap truncation diagnostic, not a max-profile accuracy score**. Extrapolating
that pathological sample to all 228 GPQA+AIME questions would require at least
about 88.8 GPU-hours and would still be invalid if every response were cut off.
The completed low-profile full sets and the official max-profile agent results
are therefore reported separately rather than presenting a misleading partial
"max" aggregate.

## High-profile paired diagnostic (2026-08-24)

A targeted paired diagnostic tested whether the low-profile misses were caused
by insufficient reasoning effort. It deliberately selected five low-wrong
samples (three GPQA, two AIME) and three low-correct controls (two GPQA, one
AIME); it is not an unbiased high-profile benchmark score.

The first pass used `reasoning_effort=high`, a 30,000-output-token cap,
`temperature=1`, `top_p=1`, seed 424242, and concurrency 1 on the normal 32K
server:

| Task | Sample | Low | High30 tokens / stop / result | High100 retry |
|---|---|---:|---|---|
| GPQA | `rec06pnAkLOr2t2mp` | correct | 658 / stop / correct | -- |
| GPQA | `rec0Arme2jcXQZnAW` | correct | 2,230 / stop / correct | -- |
| GPQA | `rec1oj2DveQWl9Rpw` | wrong | 28,987 / stop / **correct** | -- |
| GPQA | `rec2ZTsqazBZ3LTWZ` | wrong | 19,775 / stop / **correct** | -- |
| GPQA | `rec2fsnzUuvNtUYK8` | wrong | 29,999 / max_tokens / wrong | 12,949 / stop / wrong |
| AIME | `1` | correct | 938 / stop / correct | -- |
| AIME | `15` | wrong | 29,999 / max_tokens / wrong | 99,817 / stop / **correct** |
| AIME | `18` | wrong | 15,251 / stop / **correct** | -- |

At 30K, high recovered three of five low-wrong samples, preserved all three
low-correct controls, and truncated the other two. The two truncated samples
were then retried independently with a 100,000-token cap. The AIME sample
finally stopped normally with the correct answer after 99,817 output tokens;
the GPQA sample stopped normally at 12,949 tokens but remained wrong. Because
Inspect sampling streams can depend on task composition/order, the isolated
retry is a fresh same-global-seed attempt, not a deterministic continuation of
the 30K trace.

The practical conclusions are:

- Low effort materially suppressed capability in this sample: after the two
  retries, four of five selected low misses were recovered.
- Raising the token cap without raising effort would not help the original
  low runs: all low misses had already stopped normally.
- A 100K cap can matter for high effort, but is not a universal cure. One
  problem needed almost the entire budget; another remained wrong despite a
  normal high-effort stop.
- The `4/5` recovery is a paired diagnostic, not a replacement for a full
  high-profile pass@1 evaluation.

The temporary 100K server used a 104,448-token pool and reduced the logical
expert cache from 2,048 to 1,536 slots. It completed both requests without a
FreeToken restart or swap. Active dmon samples showed maximum VRAM of
24,967/24,565 MiB, mean decode-era SM of 82.4/86.0%, and maximum temperatures
of 43/45 C. Minimum host `MemAvailable` was 24.31 GiB and maximum PSI some/full
avg10 was 0.41. Three Liqbot stop/start cycles occurred during separate live
Liqbot release/drop-in activity; system logs showed intentional `Stopping` /
`Started` transitions rather than OOM or FreeToken failure. After the test,
the server was restored to the 32K pool, 2,048-slot cache, and passed a `READY`
smoke response.

## Persistent 262K context deployment (2026-08-24)

The hw5959 service was subsequently promoted from the conservative 32K profile
to a persistent 262,144-token context profile. Commit
`32a7a5add991460f387561d306b8c8f2cab25f11` exposes explicit
`--swa-full-tokens-ratio` and `--swa-num-pages` serve controls; the deployed
launcher uses the former so cache sizing no longer requires a private source
edit. The relevant arguments are:

```text
--max-running-requests 1
--max-seq-len-override 262144
--max-prefill-length 8192
--num-tokens 262144
--swa-full-tokens-ratio 0.025
--moe-cache-size 2048
```

`--max-prefill-length 8192` is the scheduler's prefill chunk size, not an
8K request limit. `/v1/models` reports both `max_model_len` and
`context_length` as 262,144. The live cache geometry contains 2,048 standard KV
pages at 128 tokens/page (262,144 tokens total), 51 SWA prefix-cache pages
(6,528 tokens), and 2,048 logical MoE expert slots. Reducing the SWA fraction
preserves the large expert cache and the single-request 262K execution path; it
reduces retained SWA prefix-cache capacity across requests rather than changing
the advertised model context.

Cache-busted, greedy, single-stream canaries used exact-length tokenizer-built
prompts. Prefill throughput is the same end-to-end approximation used above:
uncached prompt tokens divided by client-observed TTFT.

| Prompt tokens | Cached | TTFT | Approx. prefill | Decode | Wall |
|---:|---:|---:|---:|---:|---:|
| 32,000 | 0 | 17.09 s | 1,872.82 tok/s | 36.50 tok/s | 20.59 s |
| 128,000 | 0 | 63.95 s | 2,001.69 tok/s | 39.84 tok/s | 67.11 s |
| 256,000 | 0 | 132.09 s | 1,938.10 tok/s | 37.20 tok/s | 135.52 s |

An independent uncached 255,999-token repeat with concurrent telemetry measured
132.02 s TTFT, 1,939.11 approximate prefill tok/s, and 37.29 decode tok/s. Its
69 two-second samples recorded:

| Metric | Observed maximum/minimum |
|---|---:|
| FreeToken cgroup memory | 143.71 GiB max |
| `liqbot-shadow` cgroup memory | 11.49 GiB max |
| Host `MemAvailable` | 24.75 GiB min |
| Swap used | 0 GiB max |
| GPU0 / GPU1 VRAM | 31,309 / 30,907 MiB max |
| GPU0 / GPU1 utilization | 100% / 100% max |
| GPU0 / GPU1 temperature | 54 / 58 C max |
| FreeToken / Liqbot restarts | 0 / 0 max |

This directly confirms that the ordinary FreeToken and Liqbot shadow services
fit concurrently in the 256 GB host. After the long-context runs both services
remained active/running, swap was unused, and the FreeToken journal contained
no traceback, OOM, killed-process, or error line since deployment.

A forced OpenAI Chat Completions tool-call smoke also passed. DSV4 returned
`finish_reason=tool_calls`, selected `add_numbers`, and emitted the exact parsed
arguments `{\"a\":17,\"b\":25}`. Thus the context promotion did not regress the
Codex-style function-call path.

`/home/hw/bin/freetoken-dsv4-etp2-serve.pre-262k-20260824-145806`.

## Persistent 100K default output budget (2026-08-25)

The omitted-request output default was previously 32,768 tokens. Commit
`6578f718eadaf510d89835338e493b2b682b1676` makes the existing
`--max-output-tokens` server policy apply consistently to OpenAI Chat
Completions, legacy Completions, and Responses; explicit request values still
take precedence. `/v1/models` now publishes the effective policy as
`max_output_tokens` so clients and deployment checks do not need to infer it.

The persistent hw5959 launcher now adds:

```text
--max-output-tokens 100000
```

This is a decode ceiling, not a reservation. It does not preallocate 100K KV
tokens or reduce the existing 2,048-expert cache. The scheduler still clamps
generation to the remaining portion of the 262,144-token total context, so a
request cannot consume a 262K prompt and then generate another 100K tokens.

Targeted OpenAI/Responses/cache-argument tests passed 77/77. The full server
suite passed 543 tests and retained the same unrelated environment failure in
`test_muse_glimmer_parsers.py` (`ModuleNotFoundError: No module named 'tests'`).
After a clean service restart and 220-second expert-bank load:

- `/v1/models` reported `context_length=262144` and
  `max_output_tokens=100000`.
- An omitted-limit Chat request stopped naturally after 2 output tokens.
- An omitted-limit Responses request completed naturally after 2 output
  tokens.
- An explicit `max_tokens=8` Chat request remained authoritative and finished
  with `length` after 7 reported output tokens.
- FreeToken and `liqbot-shadow` remained active/running with zero restarts;
  swap stayed unused and the FreeToken journal had no error/OOM/traceback line
  after restart.

The prior 32,768-default launcher is preserved at
`/home/hw/bin/freetoken-dsv4-etp2-serve.pre-maxout100k-20260825-072818`.
